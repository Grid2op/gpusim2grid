# Injection sweep benchmarks

> This file was generated by Claude Sonnet 5 and has been fully re-read and checked by the
> authors of the paper.

Compares AC powerflow performance on the same "injection sweep" scenarios (loads/gens
resampled around a base case, topology unchanged) across multiple backends:

| Backend                               | Script                                             |
|---------------------------------------|-----------------------------------------------------|
| pandapower (CPU)                      | `pp_injection.py`                                  |
| OpenLoadFlow / pypowsybl (CPU)        | `olf_injection.py`                                 |
| lightsim2grid (CPU)                   | `ls_injection.py`                                  |
| power-grid-model (CPU)                | `pgm_injection.py`                                 |
| rustpower (CPU)                       | `rustpower_injection.py`                           |
| gpu-0DCD (GPU)                        | `gpu_injection.py`                                 |
| ExaPF.jl (CPU or GPU)                 | `export_data_for_julia.py` (Python) + `julia_exapf/exapf_injection.jl` (Julia) |
| PowerModels.jl (CPU)                  | `export_data_for_julia.py` (Python) + `julia_powermodels/powermodels_injection.jl` (Julia) |

A ninth script, `ml_injection.py`, benchmarks inference-only latency/throughput of ML
surrogate models on the same scenarios — see its own section near the end. It is not an AC
powerflow solver, so it is not part of the physics comparison above.

## Layout

Run everything from this directory (`20260831_neurips_paper/scripts`) — every path below is
relative to it.

- Grid files: `../matpowerdata` (`REF_PATH` in `scenario_utils.py`) — the same 15 matpower
  `.m`/`.mat` case files (`all_file_names` in `scenario_utils.py`) every backend reads. These
  are not checked into this repo and must be downloaded first — see
  [`../matpowerdata/README.md`](../matpowerdata/README.md).
- Benchmark results: `../raw_results` (`PATH_RESULTS`) — one JSON per run, plus optional
  `.npy` files with per-scenario voltages/flows next to it.
- Exported scenario data for the Julia backends (ExaPF.jl/PowerModels.jl only):
  `../matpower_injection_data` — written by `export_data_for_julia.py`, read by
  `julia_exapf/exapf_injection.jl`/`julia_powermodels/powermodels_injection.jl`.

## Common options

Every Python script accepts, via a shared parser (`scenario_utils.py`):

- `--sample_data_meth {fr,sable,pfdelta_n}` (default `sable`) — how loads/gens are resampled
  around the base case. `sable` (prng-based resampling, see `generate_data_from_matpower.py`)
  is the method used to produce the paper's results; `fr`/`pfdelta_n` exist in the code but
  aren't needed to reproduce them. `pfdelta_n` does not work in general.
- `--nb_pf N` (default `12000`) — number of scenarios to run per grid.
- `--seed S` (default `0`) — prng seed.
- `--add_to_name STR` — suffix appended to the output file names, to keep multiple runs from
  overwriting each other.
- `--save_voltages` — dump per-scenario complex bus voltages to `..._<case>_Vs.npy`.
- `--save_flows` — dump per-scenario branch currents to `..._<case>_As.npy` (not available on
  `olf_injection.py`/`rustpower_injection.py`).
- `--evaluate_kcl` — compute and save per-scenario KCL (power-balance) mismatch
  (`kcl_checker.py`).

`ls_injection.py`, `olf_injection.py`, `pp_injection.py`, `rustpower_injection.py` and
`pgm_injection.py` additionally accept:

- `--nb_threads N` (default `1`) — parallelize the scenario sweep. The mechanism differs by
  backend: `ls_injection.py` uses lightsim2grid's own C++ threading; `olf_injection.py`/
  `pp_injection.py`/`rustpower_injection.py` each spawn `N` worker processes
  (`multiprocessing`, `"spawn"` context); `pgm_injection.py` passes `N` straight to
  power-grid-model's own internal batch-threading.
- `--grids LIST` — comma-separated matpower filenames to restrict the run to (default: all 15
  grids in `all_file_names`, except `pgm_injection.py`, whose default is its own 5-grid
  `PGM_OK_GRIDS` — see below).

`gpu_injection.py` and `ml_injection.py` have their own option sets — see their own sections.

## pandapower (CPU)

```bash
python pp_injection.py --sample_data_meth sable --nb_pf 10000 --seed 0 --mode both --pp_backend pp_numba
```

Extra options:
- `--mode {loop,timeseries,both}` (default `both`) — `loop` calls `pp.runpp()` once per
  scenario in a plain Python loop (comparable to `olf_injection.py`); `timeseries` instead
  drives pandapower's own `run_timeseries` machinery; `both` runs both and reports both.
- `--pp_backend {lightsim2grid,pp_numba,pp_nonumba}` (default `lightsim2grid`) — which
  Newton-Raphson implementation `pp.runpp()` uses under the hood. `lightsim2grid` is
  pandapower's default whenever lightsim2grid is importable; use `pp_numba`/`pp_nonumba` to
  benchmark pandapower's *own* solver instead.

loop mode is used the experiments reported in the paper. The lightsim2grid backend is used for the
experiments in the paper too. Other option combinations were found slower (but kept for future use).

Output: `../raw_results/pp_injection_sable_10000_<pp_backend>.json`.

## OpenLoadFlow / pypowsybl (CPU)

Needs the `.mat` version of each case alongside the `.m` in `../matpowerdata` (pypowsybl loads
`<fn>at`, e.g. `case14.mat`) — see
[`../matpowerdata/README.md`](../matpowerdata/README.md#pypowsybl--olf) for how to produce
these `.mat` files (octave + MATPOWER, then `convert_to_mat.py`).

```bash
python olf_injection.py --sample_data_meth sable --nb_pf 10000 --seed 0 --save_voltages
```

Extra option:
- `--use_init_v_values` — reuse the same voltage initialization for every scenario, instead of
  warm-starting each scenario from the previous one's converged voltages
  (`VoltageInitMode.PREVIOUS_VALUES`, the default — usually faster).

Output: `../raw_results/olf_injection_sable_10000_0.json` (trailing `0`/`1` = whether
`--use_init_v_values` was set).

## lightsim2grid (CPU)

```bash
python ls_injection.py --sample_data_meth sable --nb_pf 10000 --seed 0 --save_voltages --save_flows
```

No extra options beyond the common ones. This is the reference/baseline backend the other
Python scripts reuse for grid loading and element alignment.

Output: `../raw_results/ls_injection_sable_10000.json` (+ `_<case>_Vs.npy` /
`_<case>_As.npy` if requested).

## power-grid-model (CPU) — restricted grid list

[power-grid-model](https://power-grid-model.readthedocs.io/) (PGM) is built primarily for
distribution grids. Only 5 of this benchmark's 15 canonical grids pass PGM's own base-case
solve without a "singular matrix" error — the rest are large, densely meshed transmission
grids, where PGM's sparse solver disables the pivot-perturbation technique it would otherwise
need (a known PGM limitation, see
[power-grid-model#864](https://github.com/PowerGridModel/power-grid-model/issues/864)).
`pgm_injection.py` defaults to exactly those 5 grids (`PGM_OK_GRIDS`).

**1. Checkpoint (`pgm_checkpoint.py`)** — validates a single, unperturbed base-case AC
powerflow against lightsim2grid's own solve, before trusting anything built on top of it:

```bash
python pgm_checkpoint.py --grids case14.m,case_ieee30.m,case57.m,case118.m,case_ACTIVSg500.m
```

`--grids` (default: all 15 grids) and `--pass_tol` (default `1e-6` pu) control what's checked.
This is a one-off validation step, not part of the normal benchmark run.

**2. Sweep (`pgm_injection.py`)** — the actual injection sweep, using PGM's own **Batch
Calculation** feature (`PowerGridModel.calculate_power_flow(update_data=...)`, one call per
grid covering every scenario) rather than a per-scenario Python loop:

```bash
python pgm_injection.py --sample_data_meth sable --nb_pf 10000 --seed 0 --save_voltages
```

Same common options as the other scripts, plus `--grids` (default: `PGM_OK_GRIDS`).

Output: `../raw_results/pgm_injection_sable_10000.json`.

## rustpower (CPU)

[rustpower](https://github.com/chengts95/rustpower)'s own high-level grid conversion 
(based on pandapower) isn't
voltage-comparable to this project's other backends (and pandapower grid changes the order of the 
elements), so this backend doesn't use it. Instead,
lightsim2grid owns the grid model, exactly like every other backend here: it builds Ybus and
solves the base case once (`solve_base_case`), which also populates its solver-order arrays
(Ybus/pv/pq/ref). Those arrays are captured once (`build_static_context`) and reused for the
whole sweep — since topology, gen status and voltage setpoints never change, only load P/Q and
gen P do, each scenario's `Sbus` can be rebuilt directly with numpy (`build_sbus`) without
calling back into lightsim2grid. That `Sbus` is handed to rustpower's low-level
`rustpower.solver.NewtonSolver`, so both solvers face the identical (Ybus, Sbus, pv, pq, ref)
system every scenario. `pip install rustpower` ships prebuilt wheels (no Rust toolchain
needed) — check `rustpower.features()` reports a KLU backend, which this script warns about
(not raises) if missing.

```bash
python rustpower_injection.py --sample_data_meth sable --nb_pf 10000 --seed 0 --save_voltages
```

Same common options as the other scripts, minus `--save_flows` (accepted for CLI parity but
not implemented — rustpower's low-level solver has no branch-flow output), plus `--grids`.

Output: `../raw_results/rustpower_injection_sable_10000.json` (+ `_<case>_Vs.npy` if
`--save_voltages`, in original/model bus ordering). Each case's `time_series` reports
`sbus_build_time` (building `Sbus`, pure numpy), `rustpower_setup_time`/`rustpower_solve_time`
(rustpower's own `setup_context`/`solve`, summed into `solver_time`), `total_time`
(`sbus_build_time + solver_time`) and `wall_time`. A `base_case_regression` block (computed
once per grid, not per scenario) and a `mismatch_rustpower` field (the worst per-scenario
power-balance residual over the whole sweep) give a live correctness check against
lightsim2grid — **always check these before trusting a grid's saved rustpower voltages**: on
one grid in this project's list (`case_ACTIVSg70k.m`), rustpower converges to a different,
still power-balanced Newton-Raphson root than other more robust solvers (a known multi-root risk of
undamped Newton-Raphson at that scale, not a bug in this adapter — see
`rustpower_injection.py`'s own module docstring for the full writeup).

## gpu-0DCD

Needs the `gpu-0DCD` package and a CUDA GPU.

```bash
python gpu_injection.py --sample_data_meth sable --nb_pf 10000 --seed 0 \
    --batch_size 100 --nb_iter 4 --device 0 --save_voltages --save_flows --save_kcl
```

Extra options:
- `--batch_size N` (default `100`) — number of scenarios solved together per GPU batch.
- `--nb_iter N` (default `4`) — number of fixed Newton iterations performed on GPU (no
  convergence check on GPU: this is a fixed budget, so sweeping it trades accuracy for speed —
  see `--save_kcl`/`--evaluate_kcl` to check the resulting mismatch).
- `--device N` — CUDA device index.
- `--save_kcl` — dump the per-scenario KCL (power-balance) mismatch to `..._<case>_kcl.npy`.
- `--max_batches N` (default `100`) / `--no_cap` — cap how many batches are actually timed per
  grid (tightened further on the largest grids); `--no_cap` disables this entirely (much
  slower and more likely to OOM on the largest grids).

Output: `../raw_results/gpu_injection_sable_10000_<nb_iter>_<batch_size>.json`.

## Julia setup (first run on a new machine)

`julia_exapf/` and `julia_powermodels/` are each their own Julia project (own `Project.toml`/
`Manifest.toml`). On a machine where they haven't been used yet, the first `julia --project=.`
invocation in either directory fails with something like:

```
ERROR: LoadError: ArgumentError: Package ArgParse [...] is required but does not seem to be installed:
 - Run `Pkg.instantiate()` to install all recorded dependencies.
```

Fix by instantiating the project once, from inside the relevant directory:

```bash
cd julia_exapf        # or julia_powermodels
julia --project=. -e 'using Pkg; Pkg.instantiate()'
```

This installs every dependency pinned in that directory's `Manifest.toml` (for `julia_exapf`,
that includes CUDA/CUDSS packages needed for `--backend gpu`). Needs to be done once per
directory per machine.

`CUDA.jl`/`CUDSS.jl` download their own private copy of the CUDA runtime/compiler as Julia
artifacts during instantiation — independent of any system-wide CUDA install. What's required
at the OS level is an NVIDIA driver and a visible CUDA-capable GPU (`nvidia-smi`).

To confirm the GPU side works after instantiating, in `julia_exapf` (the only directory that
uses GPU):

```bash
julia --project=. -e 'using CUDA; CUDA.versioninfo()'
```

Should print the CUDA toolchain/driver/library versions and list every visible GPU. If it
prints cleanly, `--backend gpu` is safe to use.

**Depot isolation across machines sharing `$HOME`:** Julia's package **depot**
(`~/.julia`/`$JULIA_DEPOT_PATH` by default — where downloaded package source, precompiled
caches, and downloaded artifacts like the CUDA runtime actually live) is *not* scoped to the
project directory the way a Python venv is. If `$HOME` is shared between machines with
different GPUs/drivers, point `JULIA_DEPOT_PATH` at a machine-local directory before running
Julia, e.g. `export JULIA_DEPOT_PATH=/some/local/path/julia` — otherwise one machine's
compiled GPU artifacts can collide with another's.

## ExaPF.jl (CPU or GPU) — two-step

ExaPF reads its scenarios from `.npy` files rather than generating them itself, so the same
data used by the other backends must be exported first.

**1. Export the data (Python, once per `sample_data_meth`/`nb_pf`/`seed` combination):**

```bash
python export_data_for_julia.py --sample_data_meth sable --seed 0 --nb_pf 10000
```

Writes `../matpower_injection_data/exapf_data_sable_10000/` (per-case `.npy` files +
`meta.json`). `--add_to_name` is supported here too (appended to the directory name); use
`--case <name>` to export a single grid instead of all 15.

**2. Run the solve (Julia):**

```bash
cd julia_exapf
julia --project=. exapf_injection.jl \
    --data-dir ../../matpower_injection_data/exapf_data_sable_10000 \
    --backend gpu --save-voltages
```

Options (note: dashes, not underscores):
- `--data-dir DIR` — output of step 1. If omitted, defaults to
  `../../matpower_injection_data/exapf_data_<sample-data-meth>_<nb-pf>` (so passing
  `--sample-data-meth`/`--nb-pf` instead of `--data-dir` also works, as long as they match
  what was exported).
- `--backend {cpu,gpu}` (default `cpu`) — requires a working CUDA + CUDSS install for `gpu`.
- `--batch-size N` (default `0` = all scenarios in one block) — split each case's scenarios
  into sequential chunks, bounding peak (GPU) memory.
- `--max-scen N` (default `0` = all) — solve only the first `N` scenarios of each case, for a
  quick smoke test without re-exporting with a smaller `--nb_pf`.
- `--max-chunks N` (default `128`, GPU only) — cap a grid's `--batch-size` sweep to the first
  `N` chunks instead of running every one (a timing estimate from a prefix is representative
  since every GPU chunk of a grid costs about the same).
- `--max-iter N` (default `10`) — max Newton-Raphson iterations.
- `--save-voltages` — dump per-scenario complex bus voltages.
- `--results-dir DIR` — where to write results (default `../../raw_results`, the same
  directory the other backends use).
- `--add-to-name STR` — same role as `--add_to_name` elsewhere.
- `--warmup-case FILE` — case used to pay Julia's JIT/GPU-compile cost before timing starts
  (defaults to the first case in `meta.json`).
- `--nthreads N` (default `1`) — parallelize the outer scenario-chunk loop across `N` Julia
  tasks; CPU only, ignored (forced to `1`) on `--backend gpu`. Requires launching Julia itself
  with at least `N` threads (`julia -t N ...` or `JULIA_NUM_THREADS=N`).

Output: `../raw_results/exapf_injection_sable_10000_<backend>.json`. Each case's entry has:
- `grid_load`/`grid_size`: one-time, per-grid info (case-file parse time, bus/gen counts).
- `init_powerflow`/`following_powerflow`/`block_polar_warmup`: single-scenario warm-up solves,
  each broken into `build_time`/`factorization_time`/`solve_time` (further split into
  `time_jacobian`/`time_linear_solver_update`/`time_linear_solver_ldiv`).
- `time_series`: the actual sweep — `build_time`/`factorization_time` (Jacobian construction +
  KLU factorization, reused across same-sized `--batch-size` chunks, not redone per chunk),
  `modif_time` (uploading each chunk's scenario data), `solver_time` (the Newton-Raphson
  solves), `total_time` (their sum — aggregate CPU time across tasks when `--nthreads > 1`,
  not elapsed time) and `wall_time` (actual elapsed time, used for the reported pf/s
  throughput). `diverged_early: true` means the GPU batched solve failed to converge for
  several consecutive chunks of that grid at that `--batch-size` (a known limitation of
  NVIDIA cuDSS's preview batched-LU path at specific batch sizes, not a bug) — the rest of
  that grid's chunks were skipped and the sweep moved on to the next grid.

Saved per-scenario voltages (`--save-voltages`) are not guaranteed to bit-match between two
runs of the same case that differ only in `--nthreads`/`--batch-size` (both land on valid,
power-balanced Newton-Raphson roots) — pin both settings if exact reproducibility matters.

## PowerModels.jl (CPU) — two-step, reuses the ExaPF export

A third, independent CPU AC-PF reference (alongside pandapower and pypowsybl/OLF).
PowerModels.jl has no scenario-batched or GPU solve path, so `powermodels_injection.jl` is a
plain per-scenario Julia loop — running it on far fewer scenarios than the other backends
(1000 or less) is a reasonable smoke-test/data-point size. It reuses the exact same exported
`.npy` data as ExaPF (step 1 is the identical command from the ExaPF section above):

```bash
cd julia_powermodels
julia --project=. powermodels_injection.jl \
    --data-dir ../../matpower_injection_data/exapf_data_sable_1000 --save-voltages
```

Options (dashes, not underscores) largely mirror `exapf_injection.jl`'s: `--data-dir`,
`--sample-data-meth`/`--nb-pf`, `--results-dir`, `--add-to-name`, `--save-voltages`,
`--warmup-case`, `--max-iter` (default `100`), `--nthreads`. A few are specific to this script:
- `--max-scen N` (default `0` = all) — solve only the first `N` scenarios of each case.
- `--no-warm-start-scenarios` — opt out of warm-starting every scenario's solve from the
  case's own base-case powerflow solution (the default). See below.
- `--use-ipopt` — solve with the JuMP+Ipopt-based `PowerModels.solve_ac_pf` instead of the
  default NLsolve-based `compute_ac_pf`. Much slower per scenario, useful as a correctness
  spot-check rather than a full sweep. Forces `--nthreads 1` (Ipopt isn't thread-safe here).

The base-case powerflow's starting point (flat / DC-seeded / the case file's own voltages) is
picked automatically per case (`julia_powermodels/get_init_method.jl`, mirroring
`get_init_method.py`). By default, every scenario is then warm-started from that base-case
solution (not chained scenario-to-scenario) — this avoids a known undamped-Newton-Raphson
failure mode where a handful of near-zero-load, degree-1 buses can converge to a spurious
near-zero-voltage root while still reporting `converged`; anchoring every scenario on the same
well-conditioned base case keeps one bad scenario from corrupting the rest of the sweep. See
`powermodels_injection.jl`'s own module docstring for the full explanation and the affected
grids.

Output: `../raw_results/powermodels_injection_sable_1000.json` (`_nowarmstart`/`_ipopt`
suffixes added when the corresponding flags are set, so all combinations write to distinct
files). Each case's `time_series` reports `total_modif` (per-scenario data prep),
`total_solver_time` (the actual solve calls), `total_time` (their sum — aggregate time across
tasks when `--nthreads > 1`) and `wall_time` (actual elapsed time, used for throughput).

## ML inference benchmark (PFΔ models, random-init, latency/throughput only)

Benchmarks inference-only latency/throughput of PFΔ's three ML models — CANOS-PF, GNS
(`graph_neural_solver`), PowerFlowNet — from
[MOSSLab-MIT/pfdelta](https://github.com/MOSSLab-MIT/pfdelta) (paper:
[arXiv:2510.22048](https://arxiv.org/abs/2510.22048)), on this repo's own injection-sweep
scenarios. This is **not** an accuracy benchmark: PFΔ has not released trained checkpoints, so
models here are randomly initialized from PFΔ's own config files and used purely to measure
forward-pass speed on this machine's own hardware.

Requires the `pfdelta` repo checked out as a sibling of this repo and a Python environment
with both `lightsim2grid` and `torch`/`torch_geometric` installed.

Topology + static network parameters come from a one-time `PowerModels.jl` parse per case
(never re-invoked per scenario); each scenario's load/gen is sampled the same way as the other
CPU baselines and solved with lightsim2grid, then merged into an in-memory `HeteroData`.

**1. Dump the static network(s) (once per case, ever):**

```bash
python dump_pm_static_all.py                       # every matpowerdata/*.m
python dump_pm_static_all.py --cases case118.m      # just one
python dump_pm_static_all.py --force                # redo cases whose JSON already exists
```

Drives `julia_powermodels/dump_pm_static.jl` once per case file, writing
`matpowerdata/<case>.json` alongside the source grid file. Some grids have genuine `Inf`
limits (e.g. unbounded `pmax`/`qmax`), written with `allownan=true` and read back fine by
Python's `json.load`.

**2. Run the benchmark:**

```bash
python ml_injection.py --case case118.m --sample_data_meth sable --nb_pf 2000 \
    --batch_size 8 32 128 --device cpu
python ml_injection.py --case case118.m --nb_pf 2000 --batch_size 32 --device cuda:0
```

Options:
- `--case NAME` (default `case118.m`) — matpower case (under `../matpowerdata`).
- `--sample_data_meth {fr,sable}`, `--nb_pf`, `--seed` — same conventions as the other scripts.
- `--batch_size N [N ...]` — one or more batch sizes; every requested model (`--models`,
  default all three) is timed at every batch size.
- `--n_warmup_batches N` (default `2`) — batches used for the separately-reported warmup pass.
- `--max_batches N` (default `100`) — cap on how many batches are actually timed per
  `(model, batch_size)`; `<=0` disables the cap. Prefer `--nb_pf` a multiple of every
  `--batch_size` value used — otherwise the trailing partial batch can trigger an extra
  `torch.compile` recompilation inside the timed pass (a warning is printed when this applies).
- `--device {cpu,cuda:N}` — `--launch_cpu` forces CPU regardless of `--device`.
- `--models {powerflownet,graph_neural_solver,canos_pf} [...]` (default: all three).
- `--add_to_name STR`.

Output: `../raw_results/ml_injection_<case>_<sample_meth>_<nb_pf>_<device>.json`, written (and
overwritten) after every model finishes. Contains:
- `data_generation`: the lightsim2grid solve cost, kept separate from model timing.
- per model, per batch size: a `warmup` block and a `full_sweep` block that re-times the
  entire batch set — `full_sweep` is the number to use for throughput comparisons. Each
  reports an aggregate `samples_per_s`/`ms_per_batch_mean` and a per-batch-normalized
  `ms_per_sample_batchmean`/`_batchstd`.

A `(model, batch_size)` combination that doesn't fit in VRAM records `{"error": "OOM", ...}`
in place of its `warmup`/`full_sweep` entry and the sweep continues (every larger batch size
for that model is then skipped, not re-attempted).

`torch.compile` is enabled by default for PowerFlowNet and CANOS-PF (real speedup for
PowerFlowNet; CANOS-PF mostly falls back to eager due to complex-number ops it doesn't
support). GNS is excluded from compilation entirely (`ml_model_utils.py`'s
`_NO_COMPILE_MODEL_NAMES`) — a data-dependent indexing op in its code gets miscompiled by
Torchinductor into a kernel with a wrong bounds assumption on some torch/CUDA builds, which
crashes with a device-side assert rather than a catchable exception.

TF32 matmuls are enabled (`torch.set_float32_matmul_precision("high")`) — free throughput here
since this is inference-only on random-init weights, never an accuracy comparison.

Implementation:
- `ml_pfdelta_bridge.py` — loads a case's static dict, drives lightsim2grid per scenario, and
  builds `HeteroData` objects using PFΔ's own, unmodified per-model code.
- `ml_model_utils.py` — instantiates a model from its PFΔ yaml config with fresh random
  weights (no trained checkpoint exists).
- `ml_injection.py` — the CLI driving both of the above and doing the actual timing
  (`torch.cuda.synchronize()` brackets each timed forward call on GPU).

## Notes

- All scripts warm up the target grid (one or two throwaway powerflows) before timing the
  actual sweep, and skip a grid entirely if its own base-case powerflow does not converge.
- `pp_injection.py` and `olf_injection.py` re-align pandapower's/pypowsybl's own
  bus/load/generator ordering back onto matpower's (their loaders don't preserve
  matpower's row order) — see the
  `get_*_alignment()`/`get_natural_order()` docstrings in each file if debugging a mismatch.
- Grid-specific quirks (which init method to use, known-bad grids) are documented inline in
  `scenario_utils.py` (`all_file_names` comments) and `get_init_method.py`.
- `pgm_injection.py` does **not** default to the full 15-grid `all_file_names` list — see the
  power-grid-model section above for why.
