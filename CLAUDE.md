# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project does

GPU-accelerated AC power flow for electrical grids. The Python package is `gpusim2grid`; the compiled CUDA extension is `gpusim2grid._gpusim2grid`. Four workloads, all built on a single-system Newton-Raphson (NR) core:

- **Single AC NR solve** (`AcPfGPU`)
- **N-k contingency analysis** (`ContingencyAnalysisGPU`) — trip branches, re-solve in parallel
- **Injection sweep** (`InjectionSweepGPU`) — same Ybus, many (P, Q) profiles in parallel
- **Scenario sweep** (`ScenarioSweepGPU`) — row-aligned combination of the two: row `i`'s (P, Q) profile is solved together with row `i`'s own set of tripped branches, independently of every other row. Mirrors lightsim2grid's own `ScenarioSweep` (its `BaseBatchSweep<YbusPolicy, SbusPolicy, BatchInitKind>` policy refactor); deliberately a separate class from `InjectionSweepGPU`/`ContingencyAnalysisGPU` rather than an extension of either, since the usage pattern (one topology+injection pair per row) differs from both (a shared base case with a distinct scenario set). Supports both `handle_disconnected_grid` masking and `compute_limit_violations` reporting, identically to `ContingencyAnalysisGPU` (see those sections below) — the `ScenarioSweepBatch` source implements the real `fill_mask_buffers`/`tripped_branch_table`, not the no-op stubs an earlier version shipped with.

Backed by cuDSS (sparse direct solver), cuSPARSE, cuBLAS/cuSOLVER, and Eigen (header-only, vendored at `src/eigen/`). Grid data (Ybus, Sbus, pv/pq/slack arrays, branch admittances) comes from lightsim2grid/pandapower; this package only consumes those arrays.

## Commits: the DCO signoff is mandatory

Every commit must end with a `Signed-off-by:` trailer naming **a human**, or the DCO check
fails the pull request. This is the single most common reason a PR here is red.

```
Assisted-by: Claude Code (claude-opus-5)
Claude-Session: https://claude.ai/code/session_...
Signed-off-by: Benjamin Donnot <benjamin.donnot@rte-france.com>
```

Rules:

- **A bot may not sign off.** The DCO is a legal attestation that the contributor has the
  right to submit the work; only a person can make it. `Signed-off-by: Claude
  <noreply@anthropic.com>` is not acceptable even though one or two such commits slipped
  through in the past — do not copy them.
- **The signoff must match the commit author**, so a Claude-written commit is authored by
  the human signing it off, not by Claude.
- The assistant is credited with **`Assisted-by:`**, naming the tool and the model — not
  `Co-Authored-By:`, and never as an author. This follows the kernel's convention for
  coding assistants (https://docs.kernel.org/process/coding-assistants.html).
- Set the identity once per session, then `-s` produces a matching trailer by itself:

  ```
  git config user.name  "Benjamin Donnot"
  git config user.email "benjamin.donnot@rte-france.com"
  git commit -s
  ```

- Adding the trailer to a commit that already exists needs
  `git commit --amend --no-edit -s` (and `--author="..."` if the author is wrong too),
  followed by `git push --force-with-lease`. This is the case that actually bites: the
  mistake is usually noticed only after CI has run.

`CHANGELOG.rst`, under the current development version at the top (lightsim2grid's

## Build

```bash
source env_compile.sh       # exports CUDAToolkit_ROOT, cudss_ROOT, LD_LIBRARY_PATH — edit paths for your machine
pip install --no-build-isolation .               # FP64 (double) by default
CUDA_REAL_FLOAT=1 pip install --no-build-isolation .    # FP32 (float)
CUDA_REAL_DOUBLE=1 pip install --no-build-isolation .   # FP64, explicit
```

`--no-build-isolation` matters because gpusim2grid's C++ bridge build needs
to see the `lightsim2grid` already installed in the current environment
(built from source, matching Eigen/SuiteSparse/compile flags) — not a fresh
one pip would otherwise resolve into an isolated build environment.

`scikit-build-core` (pyproject.toml) → CMake → NVCC. Requires CUDA toolkit + cuDSS ≥ 0.8.0 installed and discoverable (see `env_compile.sh` for the expected layout). Precision is a **compile-time** choice (`-DUSE_FLOAT_PRECISION=ON` or the env vars above); query it at runtime via `gpusim2grid._gpusim2grid.is_fp32` or `compilation_options.is_fp32()`.

### The NR core and the policy/strategy pattern

The central abstraction is a **templated NR loop** (`src/_cpp/contingency/driver.cuh`, `run_nr_loop<Policy>`) that runs a fixed number of iterations over a block-diagonal batch. All physics kernels (`fill_FP`, `fill_FQ`, `fill_J`, `update_Va`, `update_Vm` in `acpf_nr_kernels.{cuh,cu}`) are called by the driver, never by policies. A **Policy** decides only *when* to factorize/refactorize/solve the linear system (which `CudssBatchSolver` owns). Strategies live in `src/_cpp/contingency/strategies/`:

| Strategy enum / string | Policy file | Behavior |
|---|---|---|
| `DirectRefactorEvery` / `'direct_refactor_every'` (default) | `policy_refactor_every.cuh` | Fill J every iter; factor once, refactor every iter. Most accurate. |
| `DirectIter0Only` / `'direct_iter0_only'` | `policy_iter0_only.cuh` | Fill/factor J at iter 0 per chunk; solve-only afterward. |
| `DirectBaseCaseFactors` / `'direct_base_case_factors'` | `policy_base_case_factors.cuh` | Reuse base-case LU factors; cheapest, approximate. |
| `DirectRefactorEveryN` / `'direct_refactor_every_n'` | `policy_refactor_every_n.cuh` | Refactor every N iters (`refactor_period`). |

**Adding a new strategy = adding a policy header + an enum value + the string mapping in the Python facades; no kernel changes.** The Python-side string→enum map (`_STRATEGY_MAP`) is duplicated in `contingency_analysis/__init__.py` and `injection_sweep/__init__.py` — keep them in sync.

### Batch sources

`src/_cpp/contingency/batch_sources/` adapts the workloads to the shared block-diagonal batch the NR loop consumes: `contingency_batch.cuh` patches Ybus (subtracts tripped-branch admittances), `injection_batch.{cuh,cu}` varies Sbus from per-scenario (P, Q), `scenario_sweep_batch.{cuh,cu}` composes both — per-active-slot Ybus patches (verbatim `ContingencyBatch` logic) *and* a per-scenario dense Sbus row (verbatim `InjectionBatch` logic), with the Sbus rows pre-permuted into active-slot order at construction so compaction (disconnected scenarios dropped from the batch) and the dense Sbus row-slice copy stay consistent. Contingencies/scenarios that would disconnect the Ybus graph are skipped and their residuals set to NaN. That connectivity decision (`check_connectivity` / `compute_component_masks`, `contingency_analysis_helper.cpp`) is answered from **one DFS tree of the base graph per batch** (tree/non-tree edges, bridges, preorder subtree ranges): an N-1 trip is O(1) — connected unless the edge is a bridge, and then the masked side is a preorder range — and an N-k trip is resolved by merging the cut-off subtrees with a union-find; only asymmetric removals or a cut-off side larger than half the grid fall back to a per-contingency BFS. Don't reintroduce per-contingency graph searches there: on a 7k-bus grid that cost ~1 s per N-1 study, more than the GPU solve. Likewise the block-diagonal Ybus CSR structure (`blockdiag_csr_kernel`, `batch_pf_driver.cu`) and the per-chunk V/Ybus tiling (`tile_kernel`, `acpf_nr_kernels.cuh`) are generated on the device — at a 10k batch the host build + pageable upload and the per-slot `cudaMemcpyAsync` loops were each hundreds of ms of pure CPU time. All three `BatchSource` types are explicitly instantiated as `BatchPfDriver<...>` in `contingency/batch_pf_driver.cu` — a new source needs both the header/`.cu` pair *and* a `template struct BatchPfDriver<NewBatch>;` line there.

### Session objects and Python facades

C++ session classes (`AcPfNrSession`, `ContingencyAnalysisSession`, `InjectionSweepSession`, `ScenarioSweepSession`) keep state (converted indices, base-case factors, device buffers) on the GPU so a base-case solve is reused across many `run()` calls.

For each workload there is exactly **one** public entry point — `AcPfGPU`, `ContingencyAnalysisGPU`, `InjectionSweepGPU`, `ScenarioSweepGPU` (all exported from the top-level `gpusim2grid` package) — whose `grid` argument accepts either a solved lightsim2grid grid (extracted zero-copy via the C++ bridge when compiled in, else via the `_ls2g_utils.py` Python fallback) or an explicit `(Ybus, Vinit, Sbus, slack_ids, slack_weights, pv, pq)` array tuple for callers without a lightsim2grid grid; `isinstance(grid, (tuple, list))` picks the branch in each facade's `__init__`. In tuple mode, branch data (needed for `compute_flows`/`build_contingencies`/`set_topology`) is supplied afterward via `set_branch_data()`, and `use_bridge=True` is invalid (there's no grid to bridge to). `ScenarioSweepGPU` always extracts/requires branch data (like `ContingencyAnalysisGPU`, unlike `InjectionSweepGPU`'s optional `auto_branch_data`) since `set_topology()` needs it, not just `compute_flows()`.

Each facade is implemented in its sibling package's `gpu_facade.py` (e.g. `contingency_analysis/gpu_facade.py`) and delegates in tuple mode to that package's internal engine class — `_ContingencyAnalysisSolver` / `_InjectionSweepSolver` / `_ScenarioSweepSolver` (Python wrappers adding `_normalize_device`, the string strategy map, and `DeviceBuffer` lazy `to_numpy()` D→H copies) or the raw `AcPfNrSession` C++ binding for `AcPfGPU`. These are underscore-prefixed (except `AcPfNrSession`, a compiled binding rather than a Python ergonomics class) precisely because they are *not* a second public entry point — don't reach for them directly in new examples/docs; use the `*GPU` facade with a tuple `grid` instead. `batch_size`, `nb_iter`, `strategy`, `refactor_period` are mutable and take effect on the *next* `run()`; `max_iter_base` / `tol_base` only apply at construction. `ScenarioSweepGPU.set_topology(branch_ids_per_scenario)` (optional; a row never covered defaults to "no branches tripped") uses the same ragged `list[list[int]]` convention as `ContingencyAnalysisGPU.add_contingencies_by_branch_id`, row-aligned with `set_injections`/`set_injections_from_elements` — not lightsim2grid's dense boolean-mask API.

`ScenarioSweepGPU.set_contingency_gens(mask)` (`(n_scenarios, n_gen)` bool, row-aligned with `set_injections_from_elements`/`set_topology`; lightsim2grid PR #193 parity, same signature as its `ScenarioSweep.set_contingency_gens`) is the third contingency axis: per row it takes the generator's P (and its target Q if it does not regulate voltage) out of Sbus, re-weights the distributed slack without it, and — when the **last** generator locally regulating a bus is off — turns that bus PV→PQ *for that row only*. The injection side is Python's (`build_bus_injections(..., gen_off=)` in `_ls2g_utils.py`, using the new `InjectionElements.gen_target_q_mvar`/`gen_vreg_on`; the facade stores the element inputs so mask and injections may be set in either order; a caller using the per-bus `set_injections` must remove the injection itself). The labelling side is the session's: at `run()`, `ScenarioSweepSession::_prepare_gen_contingency` derives the set of buses that can flip (union over rows) **automatically from the mask** and, whenever it differs from the reserved set (`reserved_buses_`, growing *or* shrinking — an all-False mask is bit-identical to no mask), rebuilds `base_state_` once on a copy of the unextended ledger extended by `add_switchable_vm_buses` (one base-case setup + cuDSS analysis; the stored ctor inputs and `base_ledger_` exist for that rebuild, and any live DLPack view of the base buffers dies with it). Rows where a reserved bus is still PV identity-pin its Q row (`Contingency::pinned_buses`, emitted into the same identity-row stream as `handle_disconnected_grid` → `dVm = 0`, P row live); the base-case solve pins every reserved bus too (`AcPfNrState::d_pin_*`, wired into the single-system `NrIterBuffers` mask fields — the "n" case is lightsim2grid's PV labelling). Per-row slack weights (`_row_slack_weights`, mirroring lightsim2grid's `LSGrid::get_slack_weights_solver_without`: survivors renormalised, the storage units taking part in the slack always among them — `GenContingencyData::storage_slack_weight_bus`, since no row disconnects one; no participant left ⇒ the reference bus takes 1) travel as a `[n_active × n_slack]` array permuted into active-slot order like `h_Sbus_all_`, sliced per chunk, and consumed by the two MultiSlack kernels through `NrIterBuffers::slack_w_stride` (0 = shared base weights, bit-identical). Per-generator metadata comes from the bridge (`extract_gen_contingency_data`, `gen_contingency_data.hpp`; tuple mode raises). Refused like upstream: a remote controller or a generator on a group-controlled bus; `direct_base_case_factors`. `dim_J` / `reserved_switchable_buses` on the facade show the current structure.

`redistribute_slack` (bool, default False, mutable, also a constructor argument; `ContingencyAnalysisGPU` and `ScenarioSweepGPU`; lightsim2grid PR #216 parity, same name and semantics as its `ContingencyAnalysis`/`ScenarioSweep` option) is OpenLoadFlow's `DistributedSlack` outer loop applied *before* the solve to what a row loses: the net injection of the island `handle_disconnected_grid` masks (read off the row's own Sbus over the masked buses, minus their shunts' active power, which the AC Sbus does not carry — upstream sums the same elements one by one) plus, on a scenario sweep, the set-point of every generator `set_contingency_gens` takes out and what the row's own injections take out of the balance of the grid's set-points (`SlackRedistributionData.base_p_mw` = sn·ΣRe(grid Sbus), filled by the bridge, minus the row's ΣP with its disconnected generators put back — upstream's element-wise Σ(target − row) over generators and static generators minus the loads'; NaN in array mode without it = no such term). A line/trafo that leaves the grid connected loses nothing: the change in the losses stays with the Newton slack. The loss is shared on the slack units that stay (generators then storage units by id, weight > 1e-7, generator convention) by a verbatim port of upstream's `distribute` (`slack_redistribution.hpp`, host, once per run: proportional to the raw weights, clamped to `[min_p, max_p]` and never crossing 0 MW, a clamped unit leaving the pool; all saturated ⇒ all stay in the slack). Per row that gives a sparse `(bus, dP)` Sbus correction and the saturated units, which leave that row's distributed slack; the solve then only shares the change in the losses. Device side: `SlotSlackRedistribution` (`contingency/batch_sources/slot_slack_redistribution.cuh`, shared by both sources like `MaskStreams`) owns the per-row weights (`[n_active × n_slack]`, sliced per chunk, `slack_w_stride`) and the correction stream (scatter-added per chunk into the slot's Sbus after it was filled: never into `d_Sbus_orig`, so hot re-runs never add it twice). `ContingencyBatch::sbus_stride` became an instance method: a batch with no correction keeps the shared base Sbus (stride 0, bit-identical); otherwise every slot gets its own tiled copy (`contingency_batch.cu`). `ScenarioSweepBatch` no longer takes weights in its constructor: `ScenarioSweepSession::run()` sets weights (generator contingency and/or pre-pass) and correction on the *live* source on every path that needs it, so a pre-pass change stays a hot run. The participants come from the bridge (`extract_slack_redistribution_data`, attached by both factories; the facades re-read them when the flag is turned on, so `set_gen_p_limits` after construction is seen); a scenario sweep's per-row generator set-points from `set_gen_p_rows` (pushed by `set_injections_from_elements`, cleared by a per-bus `set_injections`: grid targets). Refused: no distributed slack, `direct_base_case_factors`, device injections (`set_injections_dlpack`). `get_slack_redistribution_report()` gives lightsim2grid's per-row `SlackRedistributionReport`. The slack active-power check follows (see Limit violations): a moved unit is checked at its new set-point, a saturated one takes no share. Without p limits nothing saturates and the converged state is unchanged. Pinned in `tests/python/test_redistribute_slack.py` against lightsim2grid's own batch and its one-off path. **Pre-pass-only units**: a unit lightsim2grid flags "can participate in the slack" (`LSGrid.set_gen_can_participate_slack` / `set_storage_can_participate_slack`: left out of the slack only because it sat at an active limit, what `bake_outer_loops(..., return_details=True)` capped) is a unit of `SlackRedistributionData` with `in_slack = 0` (empty `in_slack` = all 1), taken by the bridge in upstream's `append_participants` order: it shares the lost power within its bounds (so only away from the limit it sits at) but never enters the solve's slack weights (`row_slack_weights` skips it) and never becomes a saturated unit of a row. Pinned in `tests/python/test_can_participate_slack.py`.

`InjectionSweepGPU.set_gen_v(gen_v)` / `ScenarioSweepGPU.set_gen_v(gen_v)` (optional; `(n_scenarios, n_gen)` vm_pu, row-aligned with `set_injections`/`set_injections_from_elements`) mirrors lightsim2grid's own `modify_gen_v` and does **not** feed Sbus. A column acts on the bus its generator **regulates** — `InjectionElements.gen_v_bus` is `regulated_bus_id` mapped to solver numbering, -1 for a non-writer (`_for_each_vm_writer`: connected, `voltage_regulator_on`, not treated as off) — and that bus decides how (`gen_v_active_columns`, `contingency/gen_v_override.hpp`): **Vm-fixed** (`h_is_vm_fixed_bus_`: `pv ∪ slack_ids` *without* a Vm column in the un-extended ledger — lightsim2grid gives a slack bus nothing pins locally a free Vm + Q equation, so `pv ∪ slack` alone is wrong) → value-only reseed of `d_V_batch` right after `tile_V` (`apply_gen_v_kernel`), no Jacobian change; **held by a VoltageControl group** (`h_vc_group_of_bus_`: a remote regulator, or a local one on a group-controlled bus) → that group's per-row `v_set` in `|V_reg| + s·Q − v_set = 0` (`GenVsetSlots`, `contingency/batch_sources/gen_vset_slots.cuh`: base v_set tiled per slot, non-NaN group columns written in by `apply_gen_vset_kernel`, consumed by `vc_vrow_kernel` through `NrIterBuffers::vc_vset_stride`; |V_reg| is reseeded too, as a start value); anything else is ignored. Keying on the generator's *own* bus silently dropped every remote regulator's set-point (72 of 585 groups on a real RTE snapshot, forward and gradient alike consistently 0). A generator whose non-regulating co-located neighbour carries a stale `target_vm` (often 0.0) is why every gen_v consumer (both facades, `conflicting_gen_v_rows`, `BatchPowerFlow`'s conflict check and gradient gate) must use `gen_v_bus`, never `gen_bus`: gating on the bus alone made 60% of a 297-snapshot French-grid validation run come back NOT SIMULATED. NaN entries leave that `(row, gen)` untouched; left unset entirely, every row keeps the grid's own base-case voltage and set-points. The (n_gen,)→bus mapping is `InjectionElements.gen_bus` (`_ls2g_utils.py`, -1 for a disconnected generator so it can never alias a still-connected co-located one). `GenVOverride` (`contingency/gen_v_override.hpp`) is the shared host-side filtered/uploaded representation; `ScenarioSweepBatch` permutes it into active-slot order exactly like `h_Sbus_all_`. **Two connected generators regulating one bus with different set-points are refused, not last-writer-wins** (lightsim2grid's own `set_vm` documents last-writer-wins; |V| at a bus is unique, so no solution satisfies both), and so is a generator asking a VoltageControl group holding an SVC / hvdc station (whose set-point no batch moves, `vc_group_has_fixed_member` → `vc_pinned_v_set`) for anything but that set-point: `conflicting_gen_v_rows` (`_ls2g_utils.py`, tolerance `GEN_V_CONFLICT_TOL`, only counting driven columns (`gen_v_driven_columns`), non-NaN, not taken out by `set_contingency_gens`) flags the rows; `ScenarioSweepGPU.set_gen_v` and `BatchPowerFlow` (torch `scatter_reduce` version) report them NOT SIMULATED through `ScenarioSweepSession::set_skipped_rows` — a per-row `Contingency::skip` that `check_connectivity`/`compute_component_masks` turn into `disconnected` without touching the graph, so the row rides the existing compaction (NaN V/residual, `get_disconnected()` = 1, NOT_SIMULATED violation, zero gradient; a change is a warm source rebuild) — while `InjectionSweepGPU.set_gen_v` (no not-simulated concept) raises `ValueError`.

### Augmented Jacobian (ledger-driven NR)

When solving through the lightsim2grid bridge (the default `grid=<solved LSGrid>` path on all four facades), gpusim2grid does not solve the bare `[pvpq | pq]` system — it reproduces the **same augmented NR system lightsim2grid poses**, including in-Jacobian power-system controls: distributed slack (`MultiSlack`), HVDC angle-droop, and SVC / remote generator voltage control (`VoltageControl`). Results match lightsim2grid bit-for-bit (to ~1e-15) on both the single solve and the batched contingency/injection-sweep/scenario-sweep paths.

- **`LedgerData`** (`src/_cpp/ledger_data.hpp`) is the host-side description of the augmented Jacobian: the J sparsity skeleton (CSR, structure only), bus-keyed row/column maps (`p_row_of_bus`, `q_row_of_bus`, `theta_col_of_bus`, `vm_col_of_bus`, `q_col_of_bus`), and per-extension feature data (MultiSlack weights, HVDC droop parameters, VoltageControl controller data). It mirrors lightsim2grid's own `NRSystem`/`NRLedger`, which stays the single source of truth for the augmented structure — gpusim2grid only does the batched *numeric* fill/solve on the GPU.
- **`ls2g_bridge.{hpp,cpp}`** (`extract_ledger_data`, `make_acpf_session_from_lsgrid`, and the CA/IS equivalents) build a `LedgerData` off a *solved* `ls2g::LSGrid` — reading `get_J_solver()`, the ledger row/col accessors, and per-extension data straight off the C++ object (zero-copy, no scipy marshalling). `nullptr`/empty `LedgerData` reproduces the legacy feature-free (bare pvpq/pq) system exactly.
- **`use_distributed_slack`** (bool, default `True`, construction-time only, on all four facades): picks between the two slack formulations. `False` calls `drop_multislack_augmentation()` (`ls2g_bridge.cpp`) on the extracted ledger, deleting exactly what MultiSlack owns — the P equation of *every* participant, the theta unknown of every non-reference participant, and the `slack_absorbed` column — so `dim_J` shrinks by `n_slack` and lands on the bare `[pvpq | pq]` size. **HVDC droop and VoltageControl are preserved either way**; this switch only touches the slack. Deleting (rather than rebuilding) is valid because the augmented sparsity pattern is a strict superset of the bare one, so no entry ever has to be added. With one participant it is an exact reformulation (that row/column pair is block-triangular). With several it is a genuine model change, and combined with `init_from_n_powerflow=True` it then legitimately fails the residual check. Note it is *not* a workaround for the cuDSS batch-reordering NaN bug — measured on case300 the bare system is markedly *more* affected (833/1440 vs ~10/1440 NaN at `reordering_alg='default'`); `reordering_alg='none'` and `strategy='direct_base_case_factors'` still fix it in both modes.
- **Feature-free invariant**: the trivial ledger built for the tuple-`grid` (no-lightsim2grid) path reproduces the legacy layout exactly — P/theta on sorted(pvpq) at rows/cols `[0, n_pvpq)`, Q/vm on pq in input order at `[n_pvpq, dim_J)`. Don't break this when touching ledger code — it's what keeps the bare path bit-identical.
- **Structural supersets** (`ledger_extend.{hpp,cpp}`): the CA/SS sessions may solve a J whose pattern is a strict *superset* of lightsim2grid's — every extra entry is filled per slot by value, so one cuDSS analysis still serves the batch. Two extensions exist: `reserve_stranded_controller_slots` (one `(v_row, q_col_first)` zero per VoltageControl group whose first controller is not an SVC, see `handle_disconnected_grid`) and `add_switchable_vm_buses` (one Vm column + Q equation per bus, with the full dS pattern derived from Ybus, **appended at the end** of the ledger so no existing index moves — which is why the VoltageControl custom rows are first frozen into explicit `LedgerData::vc_v_rows`/`vc_share_rows` by `materialize_vc_custom_rows`; an empty `vc_v_rows` still means lightsim2grid's own "last `n_controllers` rows" layout). `AcPfGPU`/`InjectionSweepGPU` ledgers are never extended. `drop_multislack_augmentation` must run *before* either extension.
- **Feature kernels** are small, conditionally-gated additions layered on the same driver: MultiSlack (`adjust_slack_mismatch`/`fill_slack_feature`/`update_slack_absorbed`, gated on `slack_col>=0`), HVDC droop (`hvdc_adjust_mismatch`/`hvdc_fill_feature`, additive J slopes — forces `d_J_values` to be zeroed before `fill_J` when active; the receiving-side slope is the *exact* derivative of the flow, `k·(1−lf1)(1−lf2)·(1−2·r·line_in)` — NR converges without the last factor, the adjoint does not: it was a ~1e-4 relative error on real-grid P gradients, see `test_hvdc_droop_resistive_loss_slope_is_exact`), and VoltageControl (`vc_adjust_mismatch`/`vc_vrow`/`vc_share`/`vc_apply_step`, a bordered formulation that adds custom rows). Shared inline helpers `nr_feature_{mismatch,zero_J,fill_J,update}` (`nr_iter_step.cuh`) are called from both the single-system step and the batched `driver.cuh` loop, so CA/InjectionSweep get the augmented system "for free" once the base session carries a `LedgerData*`.
- **`presolved_v` fast path**: when the bridge is told the grid's own `V` is already converged (`init_from_n_powerflow=True`, the `AcPfGPU` default), the GPU trusts it instead of re-running NR from scratch — it factorizes J once at V0 and, for MultiSlack/VoltageControl, recovers the `slack_absorbed`/controller-Q running state (not a pure function of V) two ways: by default it's seeded directly from lightsim2grid's own converged ground truth (`LedgerData::slack_absorbed_gt`/`vc_q_gt`), needing no cuDSS solve at all; only when that ground truth isn't available (array/tuple mode) or `debug_base_case=True` is explicitly requested does it fall back to deriving that state with one solve-only correction, *without moving V* either way. It then verifies the residual. `V` stays bit-identical to the CPU solution.
- **`handle_disconnected_grid`** (`ContingencyAnalysisGPU` and `ScenarioSweepGPU`; not `InjectionSweepGPU`, whose topology never changes): the batch shares one fixed symbolic structure, so masking a contingency-islanded bus is value-only — identity its J row(s), zero its F row(s), report its V as NaN — solved on the largest connected component instead of skipping the whole scenario. Contingencies/scenarios that strand the angle reference, an HVDC end, or a *regulated* bus one of whose controllers stays live (its frozen magnitude cannot reach `v_set`; lightsim2grid's `_skip_rows_stranding_regulated_bus`) are still conservatively NaN-skipped. A VoltageControl group **every** controller of which is stranded (any size, its regulated bus live or masked too) is recovered instead — lightsim2grid PR #192 / #216 parity: its bordered voltage row is repurposed by value into `Q_first == 0` (`J[v_row, q_col_first] = 1`, `J[v_row, vm_col(reg)] = 0`, 0 on the other controllers' SVC slope slots, `F[v_row] = -Q_first`), its sharing rows are kept and pin the other controllers to 0, and the regulated bus floats as an ordinary PQ bus, matching a one-off solve with those controllers deactivated. The `(v_row, q_col_first)` slot is a structural zero the CA/SS bridge factories always reserve for every group whose first controller is not an SVC (`reserve_stranded_controller_slots`, `ledger_extend.{hpp,cpp}`; an SVC's slot already carries its slope; `acpf_nr.cu` re-stamps it to 0 every fill). Per-slot machinery: `Contingency::stranded_groups` (decided in `compute_component_masks` from `MaskConfig`'s VC group topology), the `jov`/`str` streams of `MaskEntries`/`MaskStreams` (`contingency/mask_streams.cuh`, shared by both batch sources), and `apply_J_overrides_kernel` / `vc_stranded_vrow_kernel` launched by the `nr_apply_J_masks` / `nr_apply_F_masks` composites (`nr_iter_step.cuh`) — always *after* the feature stamps and *before* the bus mask. A stranded member of a group with a live controller is left alone (the live ones hold the bus, the sharing rows keep the masked column coupled). **Automatic reference slack** (`reference_slack="auto"`, the default on `ContingencyAnalysisGPU`/`ScenarioSweepGPU`; `BatchPowerFlow` uses `"grid"` so a row's angles never depend on the other rows' topologies; lightsim2grid PR #216's `_select_ref_slack_and_masks`): with `handle_disconnected_grid` and the distributed slack, the angle reference becomes the participant stranded by the fewest rows (`choose_reference_bus`, `contingency_analysis_helper.cpp`: plain largest-component masks of every row, ties to the higher weight then the lower bus; a reference forced on the grid with `set_reference_slack_bus` is kept — the bridge hands it over as `forced_reference_bus`). A change moves the reference in the stored ledger (`move_reference`, `ledger_extend.cpp`: the new reference's theta column index goes to the old one with its Ybus/droop pattern, and the two P rows trade indices — **exactly lightsim2grid's own ledger for that reference**, pinned by `test_moved_reference_is_lightsim2grids_own_ledger`) and rebuilds the base state (SS: through `_build_base_state` → cold run; CA: its base state is now rebuildable too, the ctor inputs and the unextended ledger are stored). V is unchanged at the base case (every participant keeps its P row); a contingency row's angles differ from the `"grid"` reference by that row's own constant. `session.reference_bus` shows the one in use. `optimize_reference_slack(grid, contingency_branch_ids)` (top-level export) remains: it re-picks and re-solves on the CPU grid itself (contingency analysis only). Note that two separate sessions are only reproducible to ~1e-15 (batched GPU reductions): compare them to rounding, never bit for bit. Both sessions build their `MaskConfig` through the shared `build_mask_config` (`mask_config_builder.cuh`), and `ScenarioSweepBatch` reuses `compute_component_masks`/`build_mask_entries`/`MaskStreams` verbatim from the contingency stack.
- **Differentiable path**: the adjoint backward (`_power_flow_op.py`) indexes through the same bus-keyed maps (`p_row_of_bus`/`q_row_of_bus`/`theta_col_of_bus`/`vm_col_of_bus`, exposed on `AcPfNrSession`) rather than positional pvpq/pq slots, so gradients are correct on both the bare and augmented systems without separate code paths.

### cuDSS solver configuration

Three construction-time-only knobs select cuDSS's analysis-phase behavior, exposed identically on all four facades (`reordering_alg`, `matching_alg`, `pivot_epsilon_alg`, all strings): `ReorderingAlg` (`'default'|'btf_colamd'|'colamd'|'amd'|'nested_dissection'|'none'`), `MatchingAlg` (`'none'|'max_diag_count'|'max_min_diag'|'max_min_diag_alt'|'max_diag_sum'|'max_diag_product'|'auto'`), `PivotEpsilonAlg` (`'default'|'scaled'|'static'`). The string→enum resolvers (`_resolve_reordering_alg`/`_resolve_matching_alg`/`_resolve_pivot_epsilon_alg`) are defined once in `contingency_analysis/__init__.py` and imported by `injection_sweep`, `scenario_sweep`, and `acpf_nr` — a single source of truth (unlike `_STRATEGY_MAP`, which is duplicated per package). **Batch-mode restriction**: `MatchingAlg` values other than `NoMatching` (e.g. `MaxDiagProduct`, `Auto`) can silently produce NaN in uniform-batch mode (and even single-system in some cases) — `NoMatching` is the only value validated safe everywhere. `BtfColamd`/`Colamd` reordering only work single-system, not uniform-batch.

### Limit violations

`ContingencyAnalysisGPU.compute_limit_violations` / `ScenarioSweepGPU.compute_limit_violations` (`contingency_analysis/_limit_violations.py`, `contingency/violation_kernels.cu`, `limit_violation_types.hpp`) fuse bus/branch limit checking into the batched GPU kernel: `ViolationElementType` (`BUS`/`LINE`/`TRAFO`/`GRID`) and `LimitViolationType` (`LOW_VOLTAGE`/`HIGH_VOLTAGE`/`CURRENT`/`NOT_SIMULATED`/`DIVERGENCE`) mirror lightsim2grid's own codes exactly (`LimitViolation.hpp`, `improve_const_ref` branch), including `GRID`/`NOT_SIMULATED`/`DIVERGENCE` — but the two `GRID` violation types are written from two different layers, not both from the kernel: `DIVERGENCE` is written by `check_limit_violations_kernel` itself, for a contingency/scenario it actually ran the solver on but whose residual is NaN or exceeds `violation_tol` (the kernel already computes this residual check as a precondition to trusting `V`, so folding it into the same compact output avoids a second round trip); `NOT_SIMULATED` is written by the Python session layer (`get_violations()`) for one the pre-check dropped before it ever reached that kernel (`BatchPfDriver`'s `d_violation_count` `-1` sentinel) — the solver was never invoked at all. gpusim2grid additionally populates `value`/`limit` with the actual residual/tol for `DIVERGENCE` entries; lightsim2grid's own convention leaves those NaN/unused for `GRID`. These codes are not pybind-bound (the kernel writes raw ints; the Python facade mirrors them as `enum.IntEnum`) — keep the three in sync by construction if you touch any of them.

**A value must clear its limit by a relative margin, `violation_rel_tol`** (default `1e-9`, lightsim2grid's name, default and rule — `OperationalCheck.hpp`): CURRENT when `ka > limit·(1+tol)`, HIGH_VOLTAGE when `v > vmax·(1+tol)`, LOW_VOLTAGE when `v < vmin·(1−tol)`, in the kernel (`rel_tol` argument, `BatchPfDriver::set_violation_limits`), the numpy "n" check (`compute_violations_n(..., rel_tol=)`) and on both sessions / engines / facades (`violation_rel_tol`, in `[0, 1[`, next run). A bus a regulator holds exactly at its vmax comes out of a solve at vmax ± a few ulps, so with a bare `>` (or lightsim2grid's former `>=`) the last bit decided whether it was reported: on a 30-snapshot × 300-contingency RTE validation, 270 contingencies disagreed between the GPU and lightsim2grid's one-off solve, all on one such bus. `0` gives the bare strict comparisons; an FP32 build cannot resolve 1e-9 (use ~1e-6 there). The physical checks are unaffected (their own `physical_violation_tol_mva`/`_vm_pu`).

**Records kept: the most severe `capacity` per row *and per violation type*, not the first ones.** Every kernel scans all its elements anyway (the per-type totals stay exact), so each type (CURRENT / LOW_VOLTAGE / HIGH_VOLTAGE; LOW_Q / HIGH_Q; HIGH_P for HVDC; LOW_P / HIGH_P, generators and storage units ranked *together*) fills its own `capacity`-slot range of the row's slice as a sorted insertion (`TopKByType`, `violation_kernels.cu`: an O(1) rejection once the range is full, ties keep scan order), and `finish()` packs the ranges to the front of the slice in that type order. Severity: `|value/limit − 1|` for voltage and current (relative, so a 400 kV bus does not outrank a 63 kV one by size), `|value − limit|` for the physical checks. A row's slice is therefore `N_*_VIOLATION_GROUPS × capacity` long (`limit_violation_types.hpp`; the result structs carry it as `stride`, `get_violations()` derives it from the buffer length), `truncated` means "some type had more than `capacity`", and records are no longer in lightsim2grid's scan order — parity tests compare them as sets and separately check the ranking (`_assert_ranked`).

Limits are pulled off the grid by `extract_limits` (`ls2g_bridge.cpp`, also behind `set_limits_from_grid`); lightsim2grid hands back an **empty** vector, not a NaN-filled one, for any container whose limits were never configured (every pandapower case without thermal limits, and `get_bus_vmin_kv` likewise), so both the bus and the per-container branch limits are padded to full size with NaN there — the session's `set_limits` rejects a branch array that is not `n_lines + n_trafos` long.

`_limit_violations.py` lives under `contingency_analysis/` for historical reasons but is workload-agnostic (`ViolationElementType`/`LimitViolationType`/`LimitViolation`/`compute_violations_n` reference no session type) — `scenario_sweep/__init__.py` imports it directly rather than duplicating it. The check itself (`check_limit_violations_kernel`, `BatchPfDriver::set_violation_limits`/`upload_branch_admittances`) is generic over any `BatchSource`, keyed only on `source_.tripped_branch_table()`; wiring it up for a new `BatchSource` is a session-level port (`compute_limit_violations_`/`violation_tol_`/`violation_capacity_`/`has_limits_`/`set_limits()`/the `get_violation_*` accessors — see `ScenarioSweepSession` for the template), not new kernel work.

**Post-solve physical checks** (`compute_physical_violations` — one opt-in for the whole category, lightsim2grid's name: every record of `get_physical_violations[_n]()` has `category == PHYSICAL`, bus records first, then the PQ → PV release ones, then HVDC ones, then the slack machines' (generators and storage units ranked together), one `physical_violation_tol_mva` in MVA (plus `physical_violation_tol_vm_pu` for the one voltage comparison) and one `physical_violation_capacity` per row, per check *and per violation type* (the most severe records, see above); on all three batch facades, `ContingencyAnalysisGPU`/`ScenarioSweepGPU`/`InjectionSweepGPU`, and their `_*Solver` engines through the mixins in `contingency_analysis/_physical_checks.py`) are the detection side of three OpenLoadFlow outer loops, computed by four more per-chunk kernels in `violation_kernels.cu` launched right after `check_limit_violations_kernel`, with their own compact SoA outputs and `-1` sentinels (`BatchPfDriver::set_bus_q_check`/`set_gen_pv_release_check`/`set_hvdc_p_check`/`set_gen_p_check`, the session glue shared in `contingency/physical_checks_impl.cuh` (per-row targets through `physical_checks::RowTargets`), the CUDA-free config/result structs in `contingency/physical_checks_data.hpp` bound once as `PhysicalChecksConfig`/`BusQViolationsResult`/`GenPvReleaseViolationsResult`/`HvdcPViolationsResult`/`GenPViolationsResult` and exposed as `session.physical_checks`). They only *report*; nothing is switched or re-solved, and their records never mix with `get_violations()` (`ViolationCategory.PHYSICAL` vs `OPERATIONAL`/`SOLVER`, `violation_category()`, `LimitViolation.category` — mirrors lightsim2grid's enum). A row that was never simulated or did not converge (residual NaN or above `violation_tol`) has an *empty* entry, never a sentinel record (lightsim2grid parity). The base ("n") case gets its own report (`get_*_violations_n()`, same kernel as a 1-slot batch on `base.d_V_base`, gated on the base solve's `timings.converged` — there is no stored base residual).
- **Bus reactive capability** (`LOW_Q = 5`/`HIGH_Q = 6` on `BUS`; lightsim2grid PR #206): per bus held by a voltage-regulating machine, the reactive power it produced vs the *sum* of its machines' capability (generators, voltage-regulating storage units and HVDC stations `[min_q, max_q]` MVAr — a storage unit is a fixed term like a station; a voltage-mode SVC `[b_min, b_max]·|V|²·sn_mva`, re-evaluated per row; a generator a `ScenarioSweep` row disconnects leaves the sum through a device copy of `gen_off_`, and a bus with nothing left holding it is not checked). The "plan" (`BusQPlanData`, `contingency/bus_q_check_data.hpp`) is built by **lightsim2grid's own** `bus_q_check::build_bus_q_plan` in the bridge (`extract_bus_q_plan_from_lsgrid`, `#include <batch_algorithm/BusQCheck.hpp>`), so the routing is identical to its batch classes; the facades fetch it automatically when the flag is turned on (`set_bus_q_capability_from_grid`), tuple mode hands it in through `set_bus_q_capability`. The kernel compares against the **raw reactive residual** `imag(V_b·conj((Ybus·V)_b)) − imag(Sbus_b)` of the slot's patched Ybus: that is exactly lightsim2grid's `imag(mis_bus) + ΣQ_c` (its mismatch folds `−i·Q_c` in at controller buses and the check adds it back), because `d_Sbus` never carries a controller's Q and MultiSlack/HVDC only touch P rows — no VoltageControl state is needed. Two deliberate deviations from upstream: `element_id` is the **solver** bus id (like every other gpusim2grid record and its V array; upstream reports the grid-model id) and there is a per-row, per-type capacity (16, most severe kept) with a truncated flag. With the flag on, a plan must be set (the facades do it from the grid; an *empty* plan is accepted in array mode when no machine regulates a voltage).
- **PQ → PV release** (`LOW_VOLTAGE_AT_MIN_Q = 9` / `HIGH_VOLTAGE_AT_MAX_Q = 10` on `GENERATOR`, element_id the generator id, value/limit in kV of the regulated bus; lightsim2grid PR #216's `GenPvReleaseCheck.hpp`): the other direction of `ReactiveLimits` — a PQ generator the caller flagged as pinned at a reactive limit by an outer loop (lightsim2grid's per-generator `can_be_pv`, `LSGrid.set_gen_can_be_pv`, filled by `init_from_pypowsybl(can_be_pv=...)` from `bake_outer_loops`), at min_q with its regulated bus below its target (or at max_q and above) by more than `physical_violation_tol_vm_pu`, would regulate again. The plan (`GenPvReleasePlanData`, `contingency/gen_pv_release_check_data.hpp`) is built by **lightsim2grid's own** `build_gen_pv_release_plan` in `extract_gen_pv_release_plan_from_lsgrid` (gated on `__has_include`, `_gpusim2grid.have_ls2g_gen_pv_release`; a flagged machine is pinned at the nearer of its reactive limits -- the flag says it was frozen at one, a bake may leave it a hair inside); optional, unset = nothing flagged. Skipped per row: a masked regulated **or own** bus (a stranded machine releases nothing) and a generator the row's `gen_off` disconnects. A row's target is its own `set_gen_v` column (`set_gen_pv_release_targets`, pushed by `_push_gen_pv_release_targets`; unlike every other gen_v consumer this reads the columns of non-regulating generators, as upstream reads `modify_gen_v`); **NaN = the grid's target** (gpusim2grid's gen_v convention — upstream skips the machine on a NaN). Ranked by `|value/limit − 1|` like the other voltage checks. Pinned in `tests/python/test_gen_pv_release_violations.py`.
- **Standby SVC switch on** (`LOW_VOLTAGE_SVC_STANDBY = 11` / `HIGH_VOLTAGE_SVC_STANDBY = 12` on `SVC = 7`, element_id the svc id, value/limit in kV of the regulated bus; lightsim2grid's `SvcStandbyCheck.hpp`): an idle SVC the caller flagged as carrying a standby automaton (`LSGrid.set_svc_standby`, filled by `init_from_pypowsybl(can_be_pv=...)` from what `bake_outer_loops` left idle) whose regulated bus leaves the automaton's `[low, high]` thresholds would be switched on by OLF's `MonitoringVoltageOuterLoop`. **Routed through the release plan**, not a plan of its own: `GenPvReleasePlanData.el_type` (5 GENERATOR / 7 SVC, empty = all generators) says which element an entry is on and `GenPvReleasePlanData.standby` (empty = none) marks the standby ones — two entries per SVC, the low threshold with `at_min = 1` and the high one with `at_min = 0`, the release test verbatim — appended by the bridge from lightsim2grid's own `build_svc_standby_plan` (behind `__has_include(<batch_algorithm/SvcStandbyCheck.hpp>)`). It also carries the **release of a VSC converter station frozen at a reactive limit** (lightsim2grid's `LSGrid.set_hvdc_can_be_pv`: `el_type` HVDC = 4, `gen_id` the hvdc line id, `GenPvReleasePlanData.side` the station's end, written into each record's `side` -- `GenPvReleaseViolationsResult.side`), and the same plan carries the **release of an SVC frozen at a reactive limit** (lightsim2grid's `LSGrid.set_svc_can_be_pv`, built by its `build_gen_pv_release_plan` like a generator's; one entry, `el_type` SVC, `standby` 0, reported as `LOW_VOLTAGE_AT_MIN_Q` / `HIGH_VOLTAGE_AT_MAX_Q` on the SVC). The kernel gives the standby entries their own two groups (`N_GEN_PV_RELEASE_VIOLATION_GROUPS = 4`), never masks an SVC entry by `gen_off` nor moves it by a row's targets (`_push_gen_pv_release_targets` writes NaN in their columns), and writes each record's element type (`GenPvReleaseViolationsResult.el_type`), which `gen_pv_release_violations_from_result` reads. Pinned in `tests/python/test_svc_standby_violations.py`.
- **Distributed-slack active power** (`LOW_P = 8` / `HIGH_P = 7` on `GENERATOR = 5` / `STORAGE = 6`, element_id the container id; lightsim2grid 1.1.0's `GenPCheck.hpp`): the slack is solved *inside* the Jacobian by participation factors that know nothing about limits, so a participating machine's converged active power `target + its share of the imbalance` can leave its `[min_p_mw, max_p_mw]` (`set_gen_p_limits` / `set_storage_p_limits`, IIDM's own `min_p`/`max_p`; NaN = no limit on that side) — the condition OLF's `DistributedSlack` outer loop acts on. Per *machine* (the active split is the caller's own factors, not a convention), and **generators and storage units are one check**: the share of a machine is `node_mismatch(bus) · w / bus_raw_w` with `bus_raw_w` the raw participation of its whole bus, both families included, so the plan (`GenPPlanData`, `contingency/gen_p_check_data.hpp`, built by **lightsim2grid's own** `gen_p_check::build_gen_p_plan` in `extract_gen_p_plan_from_lsgrid`; array mode: `set_gen_p_capability`, optional — unset means nothing has a limit) carries every *participant*, limits or not, next to the reportable *entries*. The kernel needs no per-row slack-weight vector: the row's live raw participation of a bus (participants not on a masked bus, not a generator the row's `gen_off` disconnects) *is* upstream's `w_norm(bus)·total_raw_w`; `node_mismatch` is the raw active residual `real(V·conj((Ybus·V)))−real(Sbus)` of the slot's patched Ybus **plus the droop HVDC flows leaving the bus** (a station's published injection is `−p_flow`, what lightsim2grid's `mis_bus.real() − slack_absorbed·w` reconstructs), so no MultiSlack state is read either. A generator's target is the *row's*: `ScenarioSweepGPU`/`InjectionSweepGPU.set_injections_from_elements` push `gen_p[:, plan GENERATOR columns]` through `set_gen_p_targets` (`(n_rows × n_entries)`, NaN = base; a per-bus `set_injections` drops them, `PhysicalChecksFacadeMixin._push_gen_p_targets`, called from both the injections side and the plan side so they may come in either order); a storage unit's is the grid's own, negated into the **generator convention** — its value/limit are reported that way round too, like its limits and unlike the load-convention `target_p_mw`/`res_p_mw` lightsim2grid stores. With `redistribute_slack`, a unit the row's pre-pass moved is checked at its new set-point (merged into the targets) and one it saturated produces that set-point and takes **no share** (`upload_gen_p_no_share`, per-row uint8 masks by container id; left out of `bus_raw_w` — lightsim2grid's `takes_no_share`); a row where nothing is left sharing checks every unit at its target instead of reporting nothing (upstream's `anything_shared`). Pinned against lightsim2grid's three batch classes and a single `ac_pf`'s `res_p_mw` in `tests/python/test_gen_p_violations.py`.
- **HVDC droop P saturation** (`HIGH_P = 7`, lightsim2grid's name — `HVDC_P_SATURATION` is kept as an alias — on the new element type `HVDC = 4`, `side` 1 = would saturate 1→2 / 2 = 2→1, value/limit in MW): OLF's `HvdcAcEmulationLimits` first pass — for a droop line in LINEAR regime (`status_droop == 0`), `raw = p0 + k(θ1−θ2)`, `raw ≥ 0 and p1 > pmax12` or `raw < 0 and p2 > pmax21`, with `p1/p2 = hvdc_flows_pu(...)` (the NR loop's own device helper, now in `acpf_nr_kernels.cuh`). A saturated line is pinned at pmax by construction and is not checked; the reverse ("would un-saturate") case is out of scope. All the data is the base state's own HVDC arrays plus `LedgerData::hvdc_id`/`AcPfNrState::d_hvdc_id` (grid hvdc id per droop entry, replaying `fill_hvdc_droop_solver_data`'s selection in the bridge). Defined here first: lightsim2grid has no batch counterpart yet, so the tests pin it against a single lightsim2grid solve (`−res_p_side` and the droop formula on `ContingencyAnalysisCPP.get_voltages()`); keep the enum codes in sync the day lightsim2grid adds it.

**Base-case slack limits** are lightsim2grid's job, not a gpusim2grid option: OpenLoadFlow never gives a unit at its `max_p` a share of a positive mismatch, but lightsim2grid's base solve shares its own mismatch (its losses are not exactly the reference's) with every participant, so units the bake left at their limit come out a hair past it — and then in nearly every contingency (734 of 1000 on a French snapshot, 3 once capped). Call lightsim2grid's `LSGrid.cap_slack_at_active_limits()` on the grid right after its N solve, before building a session: the units its slack active-power check reports leave the slack at that limit, flagged `can_participate_slack` with their weight (the bridge then hands them over as pre-pass-only units, `SlackRedistributionData::in_slack = 0`: out of the Newton slack, still in the `redistribute_slack` pre-pass within their range), and the grid is re-solved from its own voltages until clean. A capped unit can be the angle reference: the reference then moves, its angle staying where the previous solve put it, so compare with a lightsim2grid analysis started elsewhere up to a per-row constant. Pinned in `tests/python/test_capped_slack_base_case.py` (gpusim2grid on a capped grid = lightsim2grid's own contingency analysis of it).

**Reactive-limit outer loop** (`reactive_limits_outer_loop`, opt-in, `ContingencyAnalysisGPU` only; `contingency_analysis/_reactive_limits.py`): after the batch, the contingencies whose physical checks report a switch the loop handles are re-solved ONCE, with the switches applied, in a second, smaller batch -- a `ScenarioSweepGPU` built lazily from the same grid with the same ctor options (`_rl_ctor_kwargs`; mutable settings mirrored by `_sync_second_pass`), one row per flagged contingency. Handled: `LOW_Q` / `HIGH_Q` on a bus its own machines hold (Vm-fixed, no VoltageControl group, no SVC susceptance, a generator among them) → PQ at the record's summed limit (`ScenarioSweepSession::set_pv_pq_switches` `to_pq`: the bus joins the reserved switchable set exactly like a generator contingency's, every other row keeping it PV; the limit is added to that row's Q through the facade's private `_q_delta` hook); `LOW_VOLTAGE_AT_MIN_Q` / `HIGH_VOLTAGE_AT_MAX_Q` on a frozen generator regulating its own PQ bus (no group, no group controller on it) → PV again (`to_pv`: Q row pinned through `Contingency::pinned_buses`, `|V|` re-seeded to the target by `Contingency::vm_reseed` → `apply_vm_reseed_kernel` after the V tile; its frozen Q leaves the injection); `LOW_Q` / `HIGH_Q` on **every** controller bus of a VoltageControl group of generators only, one direction (`_bus_group`: the bus' plan generators are exactly its GEN controllers of one group, no station / storage / SVC there) → each controller held at its own limit (`ScenarioSweepSession::set_vc_controller_pins`, `LedgerData::vc_elem_id` maps a controller to its generator; a row holding a group's first controller must hold them all, checked in `run()` by `_row_vc_pins`): `build_mask_entries` rewrites by value the group's voltage row into "Q_first = t" (the stranded-group rewrite with a target, on the slot `reserve_stranded_controller_slots` reserves) and each other controller's sharing row into "Q_c = t" (its two existing entries, `AcPfNrState::h_vc_ctrl_sh_*`), through the `jov` stream and a new `vcp` F stream (`vc_pinned_ctrl_rows_kernel`, in `nr_apply_stranded_vrow`); the regulated bus floats, no structure changes. `LOW_VOLTAGE_AT_MIN_Q` / `HIGH_VOLTAGE_AT_MAX_Q` on a frozen **remote** regulator → released into its group, through lightsim2grid's **held controllers** (PR #220, `LSGrid.set_hold_frozen_regulators`: such a machine keeps its seat in its group, pinned at its frozen output; `LedgerData::vc_held`/`vc_q_held`, `_gpusim2grid.have_ls2g_hold_frozen`): the second pass is built from a held copy of the grid (`_hold_frozen_grid`, same solution), whose base solve and every batch row pin the held controllers (`AcPfNrState::d_hold_*`, CA: every contingency's `vc_pinned_ctrl`; their frozen Q stays in Sbus and `vc_adjust_mismatch` subtracts it, `d_vc_qoff`), and a row releases one with `ScenarioSweepSession::set_vc_controller_releases` (`Contingency::vc_released`). `compute_component_masks` decides stranding per row on the *free* controllers (not pinned, not held-and-unreleased). The released machine's bus gets a reactive entry offset by its frozen output (`qmin/qmax_fixed = −target_q`), put back into its records by `fix_held_release_records`. Refused (`UNSUPPORTED`): a remote regulator lightsim2grid does not hold, another machine checked at its bus, a release leaving its group's first controller held, a group both pinned and released. `InjectionSweepSession` refuses a held grid. Anything else in a row's Q / release records (a group only part of which saturated, a group holding an SVC / station, an SVC, a truncated report) → `UNSUPPORTED`, not re-solved; the other physical checks neither trigger nor block. The second pass checks with the new labels through per-row skip masks of the two plans (`set_bus_q_row_skip` / `set_gen_pv_release_row_skip`, `d_row_skip` in the two kernels): a switched bus (or a pinned group's controller buses) leaves the Q check and gets a release entry (its first generator reports that it would switch back, against the bus it regulates -- the remote one and the group's `v_set` for a group), a released generator leaves the release check and its bus gets a Q entry. **Warm start** (`outer_loop_warm_start`, default on; `outer_loop_nb_iter`, None = `nb_iter`): the second pass starts each row from its first-pass voltages, as OLF continues from the current state after an outer-loop action — `ScenarioSweepSession::set_v_init_from_ptr` copies the rows device-to-device from `ContingencyAnalysisSession::v_results_ptr` into `ScenarioSweepDeviceData::d_V_init_orig`, `run()` gathers them into active-slot order on every path (`ScenarioSweepBatch::set_v_init_from_orig`, `gather_v_rows_kernel`: a non-finite entry, a bus the first pass masked, takes the base V — a NaN would poison the zeroed Ybus entries of a tripped branch), and `prepare_Ybus_batch` copies each chunk's slice over the tiled base V, *before* the gen_v and |V| reseeds. The linear unknowns (`slack_absorbed`, controller Q) still restart from the base: the Newton iterate does not depend on their start. On a real French snapshot it saves one iteration (3 warm ≈ 4 cold). Rows of a last, partial chunk smaller than `outer_loop_min_last_chunk` (default 250) are `LEFT_OUT`; a non-converged second pass is `DIVERGED`; both keep the first pass. Re-solved rows are copied into the CA's device buffers (`ContingencyAnalysisSession::overwrite_rows` from `ScenarioSweepSession::v_results_ptr`/`residuals_ptr`), their violation lists merged by the facade. Pinned against one-off lightsim2grid solves of the grid rebuilt with the switches (voltages and physical records, switched machines flagged `can_be_pv`) in `tests/python/test_reactive_limits_outer_loop.py`, for groups `test_reactive_limits_outer_loop_groups.py`, for held controllers `test_hold_frozen_regulators.py`.

### Zero-copy interop (DLPack)

`dlpack_export.{cu,cuh,hpp}` exports device voltage buffers as DLPack capsules (`v_base_dlpack()`, `v_results_dlpack()`) for zero-copy `torch.from_dlpack()` / `jax.dlpack.from_dlpack()`. **These capsules alias live GPU memory** — a subsequent `run()` overwrites them in place; clone the tensor if you need a snapshot, and keep the session object alive while the tensor is in use. `ScenarioSweepSession` also *imports* DLPack tensors (`set_injections_dlpack`, `set_gen_v_dlpack`, the `solve_JT_batch_dlpack` inputs): importers validate dtype/device/shape/contiguity (`check_dl_input`), consume the capsule per the protocol, take a `producer_stream` (torch's `current_stream().cuda_stream`) they wait on through an event — session streams are `cudaStreamCreate` (blocking w.r.t. the legacy default stream) but torch user streams are not — and host-sync before returning, since a torch temporary may be recycled by its caching allocator as soon as the call returns. Never remove that sync.

### Differentiable power flow

`src/gpusim2grid/differentiable/` wraps `AcPfNrSession` in a `torch.autograd.Function` (`PowerFlowFunction`, `solve_power_flow`). Backward uses the adjoint method (implicit function theorem): it solves Jᵀλ = x̄ via `AcPfNrSession.solve_JT_dlpack` reusing the converged factorization. Sbus is split into real/imag tensors because autograd needs real tensors. Sign conventions and the x-space projection are documented at the top of `_power_flow_op.py` — read it before touching gradients.

**`BatchPowerFlow`** (`differentiable/_batch_pf.py`) is the batched, ML-facing entry point: built from a solved lightsim2grid grid, it owns a `ScenarioSweepGPU` and takes lightsim2grid-`ScenarioSweep`-style per-element inputs — `load_p`, `load_q`, `gen_p`, `gen_v` (all differentiable) and the boolean `line_status`/`trafo_status` masks (**True = connected**, grid2op's convention, unlike lightsim2grid's `set_contingency_lines` where True = tripped). The element→bus assembly is plain torch (`index_add` mirroring `build_bus_injections`), so autograd gives the `load_p`/`load_q`/`gen_p` VJPs for free; an internal `_BatchPowerFlowOp` maps `(P, Q, gen_v) → V` and its backward does the batched adjoint. Its gradient is verified against finite differences in `tests/python/test_batch_power_flow.py` (gradcheck + explicit central differences for every input — keep it that way when touching any of this). The `gen_v` gradient has a direct term (`Re(e^{-jθ}·ḡV)` at the Vm-fixed bus, Python side) and an indirect one (`−λ·∂S_calc/∂Vm_k`, the dS/dVm column `fill_J` never stores for a Vm-fixed bus, computed per slot on the patched Ybus by `gen_v_adjoint_kernel` through a Ybus transpose-position map); a column driving a VoltageControl group instead gets λ at the group's voltage row (`vc_v_row_of_group`; `∂F_v/∂v_set = −1`, the injection sign; 0 on a row `handle_disconnected_grid` stranded the group, `get_row_stranded_vc_groups`, and for a pinned group). **Tied set-points share one derivative**: columns regulating the same bus must agree on a row, so only the derivative along the tie exists, and it is split equally between the columns that apply on that row (non-NaN, not off) — lightsim2grid's `get_gen_v_share`; giving each column the whole bus derivative (as before) made a group moved together see n× the gradient. NaN entries get 0. The remote set-point is far more nonlinear than a local one: a central difference at h = 1e-3 pu is ~20% off on some real remote regulators and h = 1e-2 can diverge the row, so validate those with h ≲ 1e-5. `torch.autograd.gradcheck` runs many forwards before it back-propagates the first output, so it needs `snapshot_jacobian=True` (the default alias mode refuses that pattern through the `run_counter` guard). A snapshot also requires the session's batch *source* to be the one of its own forward (active-slot map and mask streams are read from the live source at backward time): a hot forward in between is fine, a topology/`gen_status`/row-count change is refused through the `source_build_counter` guard. **`gen_status`** (`(n_scen, n_gen)` bool, True = connected) is the third, discrete contingency input: it maps to `ScenarioSweepGPU.set_contingency_gens`, with the injection correction done in torch (the off generator's P is not added, a non-regulating one's target Q leaves the constant term through `InjectionElements.gen_target_q_mvar`/`gen_vreg_on`, and its `gen_v` column is NaN'd so it can never clobber a still-connected co-located generator). Gradient rules that follow: an off generator's `gen_p`/`gen_v` get 0; on a row where a bus is *released* (PV→PQ) its `load_q` gradient is live and any `gen_v` there is 0 (`ScenarioSweepSession::get_row_pv_to_pq`, captured per forward); on a row where a reserved bus is still PV, `BatchPfDriver::solve_JT_batch` zeroes λ at every identity row of the chunk's mask stream (`zero_identity_rows_kernel`, masked P/Q rows and pinned Q rows alike) right after the cuDSS solve — an identity row `e_c` makes λ_r absorb `x̄_c − Σ J[r',c] λ_r'` while leaving every other λ exactly the reduced system's, and that λ_r would otherwise surface as a Q gradient on a frozen equation and be contracted by `gen_v_adjoint_kernel` with `∂Q_k/∂Vm_j` for the neighbours. **`redistribute_slack`** (`from_lsgrid(..., redistribute_slack=)`, mutable): the pre-pass runs *in the forward* so its correction is in the autograd graph — the rows' masks come from `ScenarioSweepSession::preview_row_masks` (host, on a copy, cached until the topology changes), `lost` and the participants' set-points are torch expressions of the inputs, the OLF loop runs on the host (`_slack_distribute_rows`) to fix the clamped set, and dP is rebuilt in torch with that set fixed (the host's exact values plus the linear map's derivative, straight-through); the saturated units reach the session through `set_external_slack_saturation` (only the row weights are rebuilt; exclusive with the session's own `redistribute_slack`). With the clamped set fixed the free units absorb the lost power by their weights exactly as the Newton slack would, so a masked island's injections and a disconnected generator's `gen_p` have a **zero** local derivative, and so does a clamped unit's own `gen_p` (a constant-correction pre-pass would get that one wrong); FD-checked in `tests/python/test_redistribute_slack.py`. **Call-to-call state**: a `forward()` without `line_status`/`trafo_status` (resp. `gen_status`) after one that had them hands the session an all-empty trip list (warm source rebuild) resp. an all-False mask (cold, since the reserved structure is released) — the same inputs always give the same answer whatever ran before (`TestCallToCallState`).

The C++ pieces this rests on (all `ScenarioSweepSession`, DLPack in/out so a JAX front-end can reuse them):

- **Driver persistence** — `run()` picks a path against `ScenarioSweepDriverConfig` (the snapshot of n_scenarios/batch_size/strategy/cuDSS config/scaling/mask mode/`fixed_batch_capacity`/base-state generation taken when the driver was built): *cold* (new `BatchPfDriver`: allocation + cuDSS ANALYSIS; `driver_build_counter`), *warm* (only the topology or generator mask changed: a new `ScenarioSweepBatch` built with `forced_batch_size` = the live capacity and swapped in by `BatchPfDriver::replace_source`, no analysis; `source_build_counter`), *hot* (only injections/gen_v changed: one device gather). The policy's `factorized_` flag survives, so reused runs REFACTORIZE only; `mark_reused` zeroes the one-time timing fields so a reused run reports `t_analysis_ms == 0`. Sbus rows live in a canonical ORIGINAL-row-order device buffer (`ScenarioSweepDeviceData::d_Sbus_orig`, filled from numpy or straight from a torch tensor via `set_injections_dlpack`) and are gathered into active-slot order on the device (`gather_rows_kernel`) — the host permutation is gone. `fixed_batch_capacity` uses `batch_size` verbatim as the chunk capacity (no rebalancing over the active count) so the batch stays one chunk whatever rows get islanded. `v_results_dlpack` memory is now overwritten in place across reusing runs (freed only by a cold rebuild). The other two batch sessions still rebuild per `run()`; `replace_source`/`mark_reused` are generic on the driver if they ever want the same.
- **Converged Jacobian** — `keep_final_jacobian` makes `_solve_chunk` refill `d_J_values_batch` at V_final (`nr_fill_J_at_current_V`, the single definition of the fill sequence, shared with the NR loop) after the post-loop residual and before the NaN masking; requires one chunk (the driver throws otherwise).
- **Lazy batched adjoint** — `BatchPfDriver::solve_JT_batch` builds `BatchAdjoint` on its first call only: host counting-sort transpose of the J skeleton + `d_J_to_JT` position map, capacity-sized buffers, a second `CudssBatchSolver` over Jᵀ (one ANALYSIS with the forward's config); every call permutes the values (`transpose_gather_values_kernel`), FACTORIZES once then REFACTORIZES (skipped for a second backward on the same forward), SOLVES, and works in original row order both ways (dropped rows → 0, non-finite rhs → 0). Counters/timings are surfaced as `BatchTimings.adjoint_*` / `t_adjoint_*` (cumulative per driver life, not part of the run() totals). Alias mode reads the chunk buffers (`run_counter` guard on the Python side); snapshot mode passes cloned `j_values_dlpack()` / `ybus_values_dlpack()` / V back in.

### Types and timing

- `dtypes.hpp` defines `real_t` (`float` or `double` per compile flag) and the Eigen/complex aliases. **Use these aliases in new solver code; never hardcode `float`/`double`.**
- `timing_utils.hpp` defines `TimingEntry` (`gpu_ms` via CUDA events vs `wall_ms` after sync), `AcPfTimings` (single solve), and `BatchTimings` (contingency + injection; exposed to Python under the legacy alias `ContingencyTimings`). Timings carry per-phase breakdowns and are surfaced on every session.
- **One-time CUDA init is its own bucket, not compute.** CUDA-context creation plus the cuSPARSE/cuDSS `dlopen`+PTX-JIT costs tens of ms on the first session in a process and scales with nothing. It is measured as `t_context_init_ms` — from `AcPfNrState::ctor_clock_` (the *first-declared member*, because the `CudaStream` member triggers context creation before the constructor body runs) through the cuSPARSE/cuDSS descriptor setup, plus the batch solver's own `CudssBatchSolver::context_init_ms()`. It is excluded from `t_gpu_compute_ms()` and added as a separate term of `t_grand_total_ms()` / the `to_dict()` `"context_init"` bucket. **Call `gpusim2grid.warmup()` (top-level export, `warmup.cu`) before any timed region** — it pays that cost up front via a throwaway 2×2 cuSPARSE SpMV + cuDSS analyze/factorize/solve (single-system *and* uniform-batch) and short-circuits on repeat calls. Both `benchmarks/contingency_analysis.py` and `benchmarks/injection_sweep.py` call it, which also covers the `run_*_sweep.py` runners (they spawn those two as subprocesses).
- **cuDSS factor statistics** ride along on `BatchTimings`: `cudss_lu_nnz` (`CUDSS_DATA_LU_NNZ`, the fill-in of *one* system — the uniform batch shares the pattern) and `cudss_mem_{device,host}_{permanent,peak}_bytes` (`CUDSS_DATA_MEMORY_ESTIMATES[0..3]`, the whole chunk), read by `CudssBatchSolver::refresh_factor_stats()` after every ANALYSIS, outside the timers. To size a Jacobian no session builds yet (e.g. a structural superset for a new outer loop), `_gpusim2grid.benchmark_cudss_batch_raw(dim, indptr, indices, data, batch_size, ...)` runs that same `CudssBatchSolver` on any CSR matrix and returns per-phase wall ms, those statistics and a residual check.
- Beware the two timing scopes when comparing against an external stopwatch: the base-case solve (`t_base_case_solve_only_ms`) happens at **construction**, while `t_analysis_ms` and the per-chunk totals happen inside `run()`/`compute()`. `t_gpu_compute_ms()` sums all three, so it is only comparable to a stopwatch spanning construction *through* `compute()`.

## Conventions

- **Branch admittances are always the Kron-reduced *effective* ones, and are named `*_eff`**: `yff_eff`/`yft_eff`/`ytf_eff`/`ytt_eff` (`h_*_eff_`, `d_*_eff` on the host/device side) are lightsim2grid's `yac_eff_*`, never the raw `yac_*`. They differ only for a *half-open* branch (`init_from_pypowsybl(..., keep_half_open_lines=True)`: connected on one side, the open end Kron-reduced out and relabeled to bus `-1`), where the raw value at the energized bus is the full series admittance while the effective one is just what survives the reduction (line charging; exactly 0 for an ideal trafo). Patching Ybus with the raw value on a trip would remove an admittance the base case never had, so `build_contingency_from_branch_ids` also skips triplets touching a `-1` endpoint. `tests/python/test_half_open_lines.py` pins this against `ContingencyAnalysisCPP`.
- **Branch ordering is lines-then-trafos**: branch index `c < n_lines` is line `c`; `c >= n_lines` is trafo `c - n_lines`. This matches lightsim2grid's `add_all_n1()` and is assumed by `build_contingencies`, branch-flow output, and the test reference helpers in `conftest.py`.
- The pybind module is `_gpusim2grid` (not the CMake `project()` name). New bindings go in `python_bindings.cpp` and must register enums *before* any binding that uses them as a default argument.
